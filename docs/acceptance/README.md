# 任务验收记录

每个行为或构建/发布机制修改一份记录，由 agent 维护。新会话先读取对应任务记录和当前差异，不依赖上一会话的口头结论。协作动作以根目录 [AGENTS.md](../../AGENTS.md#验收证据表) 为准，JSON 格式只有 `scripts/check-acceptance.mjs` 一个生成和检查入口。

## 改前创建

```powershell
node scripts/check-acceptance.mjs --init 2026-10-04-example
```

文件创建为待验收，已有文件不会覆盖。先填写标题与 `expectation` 中的真实输入例子、期望结果、不变规则、失败回退，再修改实现。`startedFrom` 保存开始时的提交；补记历史任务时明确说明是补记，不能声称此前已有这些记录。

## 修改中补证据

`checks` 的各项分别检查原故障/新行为、普通路径、其他分支、后置改写、最终检查、周边规则和最终产物。格式通过 `--init` 获取。状态只能如实填写：

- `unverified`：尚未验证，或证据未闭合；会阻止发布。
- `failed`：已验证但失败；会阻止发布。
- `verified`：有实际通过证据，必须附 `reason` 及非空 `evidence`。
- `not_applicable`：该路径确实不存在，必须写原因。原故障/新行为、普通路径、周边规则和最终产物不能免验。

将命令输出、匿名输入与独立核对结果存入 `docs/acceptance/evidence/`，用 `.txt` 保存日志（仓库忽略 `.log`）。不提交姓名、人员编号、私有完整浏览器状态、令牌或原始私有文件。真实文件应在本地独立核对，仅保存脱敏结果及所用输入的说明/校验信息。不能把测试源码、旧导出或自己写的“已通过”文字当成实际运行证据。

每个证据引用填写 `path`、`summary`、`sha256`。计算证据哈希：

```powershell
node scripts/check-acceptance.mjs --evidence-hash docs/acceptance/evidence/example.txt
```

文本证据统一按 LF 计算 SHA-256，二进制按原字节计算。删除或修改证据后旧引用会失败。计数结果独立按业务定义重算，避免与实现共用同一个错误统计函数。

## 交付检查

最后核对实际文件和期望，填写 `answers` 的三个交付问题，并填写 `review` 的三个交付后复盘问题。

`review` 是硬门，不是可选总结。它必须回答：

- `missedScope`：这次哪里可能没有做到，怎样查过；
- `rootCause`：这次真正的根因是什么，不能只写现象；
- `earlyDetection`：以后类似任务在什么时间点、用什么动作或失败信号提前发现。

三个字段任一为空，单任务检查和整体发布检查都会失败。

`answers` 的三个问题仍然保留：

1. `originalFailure`：原来的错误怎样被发现？引用修改前失败、修改后通过的证据。
2. `laterChanges`：后面还有谁可能改坏结果？引用其他分支和后置改坏测试，或说明不存在的原因。
3. `finalArtifact`：哪份本次最终产物证明要求达到了？引用实际入口输出及独立核对。

在验证对应文件完成后计算指纹，填入 `testedVersion`，再检查单个任务：

```powershell
node scripts/check-acceptance.mjs --fingerprint
node scripts/check-acceptance.mjs --record 2026-10-04-example
```

指纹覆盖 Git 管理及未忽略的新文件，按 Git 规范化内容计算，Windows CRLF 与 Linux LF 一致；排除本层任务 JSON、证据目录和本地 `.cursor/`。证据另验哈希，故更新证据不会造成版本循环。代码、测试、配置或作为输入的仓库文件变更后，旧版本不会被当作当前证据。仓库外输入必须在证据中说明并独立核对，脚本无法自动发现其变化。

不能只刷新指纹，把旧材料说成新验证。原始失败证据可以来自开始版本，最后通过证据必须对应本次所验文件。已完成历史任务保留原证据；新的改动需要新的当前版本记录。

整体发布检查不接受任务筛选：

```powershell
node scripts/check-acceptance.mjs
```

全部登记任务必须材料完整，且至少有一个对应当前文件版本的通过记录。任何待验收任务都会阻止发布，即使另一个任务已经通过；取消待验收任务需 owner 明确裁决。GitHub Pages 在 `npm run verify` 后、上传产物前调用这条命令，失败不进入上传和部署。

业务现场验收按原授权边界由 owner 操作或明确授权 agent 自行运行。本地/预览版本的实际入口产物可以作为发布前证据，不要求先部署才能验收。开发提交可以保存尚未验收的工作，但不能报告为业务验收通过。

## 检查的限度

脚本校验结构、材料存在、文件哈希、必查项、版本和交付后复盘三项；不会执行记录中的任意命令，也不证明影响范围完整、测试判断正确或人工材料真实。JSON 和检查程序仍可被修改，技术上也无法约束聊天中的完成声明。自动检查通过后仍要对照 owner 的业务例子判断是否达到要求。

本机制的真实入口是 Node CLI 与发布配置；它的验收使用独立临时仓库，不需要浏览器。仓库内另有补记的航班均衡待验收记录，保存“真实页面与新导出仍未验收”的事实；不能为了让发布检查通过而删除或填成通过。
